# KMG Security AI Agent

## Назначение

KMG Security AI Agent — прототип автоматизированной проверки информационной безопасности Test Project в процессе разработки.

Agent анализирует исходный код проекта без внесения изменений в проверяемый репозиторий и формирует отчёт о соответствии требованиям информационной безопасности.

Основные компоненты:

* статический анализ исходного кода;
* специализированные проверки требований ИБ-01 — ИБ-08;
* Semgrep для дополнительного поиска потенциальных уязвимостей;
* анализ уровня риска;
* AI-анализ security findings с использованием модели Qwen;
* генерация JSON и Markdown отчётов;
* Security Gate для интеграции с CI/CD.

## Проверяемые требования

Agent содержит отдельные проверки следующих требований:

| ID    | Требование                                                                                            |
| ----- | ----------------------------------------------------------------------------------------------------- |
| ИБ-01 | Административная функциональность доступна только администратору с серверной проверкой роли           |
| ИБ-02 | Валидность сессии или токена проверяется сервером при каждом защищённом запросе                       |
| ИБ-03 | Клиент-серверный обмен защищён TLS версии не ниже 1.2 с безопасными криптографическими параметрами    |
| ИБ-04 | Персональные данные и пароли защищаются с использованием предусмотренных криптографических механизмов |
| ИБ-05 | Локальный журнал аудита защищён и предусмотрен механизм его передачи на сервер                        |
| ИБ-06 | README или техническая документация содержит ссылки на требуемые нормативные документы                |
| ИБ-07 | Реализован проектный аудит пользовательской активности и событий базы данных                          |
| ИБ-08 | Экспорт персональных данных доступен только администратору и регистрируется в журнале аудита          |

Каждая проверка возвращает статус `PASS` или `VIOLATION`.

При обнаружении нарушения формируется структурированная запись:

* ID требования;
* формулировка требования;
* файл;
* строка;
* фрагмент исходного кода;
* объяснение нарушения;
* критичность;
* рекомендация по исправлению.

## Запуск проверки

Для запуска проверки без AI:

```bash
python -m security_agent.agent --no-ai
```

Agent выполняет:

1. проверки ИБ-01 — ИБ-08;
2. статический анализ Semgrep;
3. анализ уровня риска;
4. генерацию отчёта.

AI можно включить после настройки переменных окружения.

## Переменные окружения

Для AI используются:

```text
AI_PROVIDER=openrouter
AI_API_KEY=<API_KEY>
AI_MODEL=qwen/qwen3.8-27b:free
```

Секретный API-ключ не должен добавляться в Git.

Файл `.env` находится под исключением `.gitignore`.

Для демонстрации используется одна выбранная LLM-модель Qwen. Переключение между несколькими моделями во время одной проверки не используется.

## AI-анализ

AI используется как дополнительный аналитический слой поверх результатов статического анализа.

В модель передаются структурированные данные security finding:

* правило;
* файл;
* строка;
* severity;
* impact;
* likelihood;
* confidence;
* описание обнаружения.

AI должен вернуть:

```text
VERDICT: TRUE_POSITIVE / FALSE_POSITIVE / NEEDS_REVIEW

RISK: LOW / MEDIUM / HIGH / CRITICAL

EXPLANATION:
...

RECOMMENDATION:
...
```

AI не заменяет детерминированные проверки ИБ-01 — ИБ-08.

Если модель недоступна, превышены ограничения API или выполнение AI-анализа невозможно, проверка переводится в аварийное состояние с кодом выхода `2`.

## Ограничение контекстного окна

Для работы с большими проектами Agent не должен передавать весь репозиторий в LLM одним запросом.

Используется поэтапный подход:

1. исходный проект анализируется локальными инструментами;
2. статический анализ выделяет конкретные security findings;
3. для AI выбираются только релевантные findings;
4. в контекст передаются структурированные сведения и необходимые фрагменты кода;
5. при большом количестве findings обработка выполняется порциями.

Таким образом, размер передаваемого в LLM контекста не зависит напрямую от полного размера репозитория.

## Отчёты

Agent формирует два основных формата отчёта:

```text
security-report.json
security-report.md
```

JSON предназначен для автоматической обработки CI/CD.

Markdown предназначен для просмотра человеком и защиты проекта.

Отчёт содержит:

* commit ID проверяемого проекта;
* время начала проверки;
* время окончания;
* длительность;
* общий результат;
* количество нарушений;
* статус каждого требования;
* конкретные нарушения;
* результаты Semgrep;
* сводку уровней риска.

Commit ID берётся непосредственно из проверяемого Git-репозитория, поэтому отчёт можно сопоставить с конкретной версией Test Project.

## Security Gate

После завершения анализа Security Gate определяет результат pipeline.

```text
Exit code 0
```

Нарушений требований ИБ не обнаружено. Pipeline может продолжаться.

```text
Exit code 1
```

Обнаружены нарушения требований ИБ. Pipeline должен быть заблокирован.

```text
Exit code 2
```

Проверка не выполнена корректно. Например:

* невозможно прочитать отчёт;
* ошибка разбора проекта;
* недоступна AI-модель;
* превышены необходимые ограничения выполнения.

Такое состояние считается аварийным.

## CI/CD

Agent интегрируется в GitHub Actions отдельным шагом.

Общая последовательность:

```text
Checkout
   ↓
Install dependencies
   ↓
Information Security Checks
   ↓
Security Agent
   ↓
Security Gate
   ↓
Pipeline result
```

Пример запуска:

```yaml
- name: Run Security Agent
  run: |
    python -m security_agent.agent --no-ai

- name: Run Security Gate
  run: |
    python security_gate.py
```

На финальном варианте pipeline AI включается после завершения настройки AI-компонента.

## Принцип отсутствия изменений в Test Project

Проверяемый репозиторий рассматривается как read-only источник данных.

Agent не должен:

* изменять исходные файлы;
* изменять Git history;
* изменять конфигурацию проекта;
* создавать security reports внутри проверяемого проекта.

Рабочие отчёты и временные результаты должны храниться во внешнем каталоге.

## Разделение IS и non-IS findings

Детерминированные проверки ИБ-01 — ИБ-08 являются основанием для блокировки pipeline.

Дополнительные результаты статического анализа, которые не относятся непосредственно к требованиям информационной безопасности, должны отображаться отдельно и не должны автоматически блокировать pipeline.

## Воспроизводимость

Проверка запускается без интерактивного участия пользователя:

```bash
python -m security_agent.agent
python security_gate.py
```

Для каждого запуска фиксируется commit ID проверяемого проекта.

Время выполнения одной проверки должно оставаться в пределах установленного хакатоном ограничения — не более 30 минут.

## Ограничения прототипа

Текущая версия является прототипом и имеет следующие ограничения:

* точность AI-анализа зависит от доступности и ограничений выбранной модели;
* Semgrep может выдавать потенциальные findings, требующие дополнительной проверки;
* статический анализ не способен доказать корректность всех runtime-сценариев;
* некоторые требования безопасности требуют анализа архитектуры и конфигурации, а не только исходного кода;
* результаты AI должны рассматриваться совместно с детерминированными проверками.

## Нормативная база

Проверяемые требования основаны на технической спецификации Test Project и нормативных источниках, приведённых в разделе «Нормативные источники» данного README.

Основные источники:

1. Закон Республики Казахстан «О кибербезопасности».
2. Закон Республики Казахстан «О персональных данных и их защите».
3. Постановление Правительства Республики Казахстан № 832.
4. СТ РК ISO/IEC 27001-2023.
5. СТ РК ISO/IEC 27002-2023.
6. СТ РК 1073-2007.

```text

```
