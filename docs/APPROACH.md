# KMG Security AI Agent — описание подхода

## 1. Цель решения

KMG Security AI Agent предназначен для автоматизированной проверки информационной безопасности программного проекта в процессе разработки.

Основная задача Agent — проверить исходный код Test Project на соответствие требованиям ИБ-01 — ИБ-08, обнаружить потенциальные проблемы безопасности, сформировать структурированный отчёт и передать результат в CI/CD Security Gate.

Решение работает без изменения исходного кода проверяемого проекта.

## 2. Архитектура решения

Архитектура состоит из нескольких уровней:

```text
Test Project
     |
     v
Project Parser
     |
     +----------------------+
     |                      |
     v                      v
AST Security Checks      Semgrep
     |                      |
     +----------+-----------+
                |
                v
          Risk Analyzer
                |
                v
             Qwen AI
                |
                v
        Report Generator
          /          \
         v            v
      JSON          Markdown
         |
         v
    Security Gate
         |
    +----+----+
    |         |
   PASS     BLOCK
```

### Project Parser

Для анализа Python-кода используется AST-представление исходных файлов.

AST позволяет анализировать структуру программы без выполнения проверяемого приложения. Agent может определять функции, декораторы, вызовы, маршруты, конфигурационные значения и другие элементы исходного кода.

### Security Checks

Для каждого требования ИБ-01 — ИБ-08 реализован отдельный проверяющий модуль.

Проверки анализируют именно те признаки, которые необходимы для соответствующего требования. Например, проверяется наличие административных ограничений, серверной проверки сессии или токена, параметров TLS, механизмов хеширования паролей, аудита и защиты экспорта данных.

Результат каждой проверки имеет статус:

* `PASS` — нарушение не обнаружено;
* `VIOLATION` — обнаружено нарушение.

При нарушении сохраняются ID требования, местоположение, фрагмент кода, объяснение, критичность и рекомендация.

### Semgrep

Semgrep используется как дополнительный слой статического анализа.

В отличие от специализированных проверок ИБ-01 — ИБ-08, Semgrep выполняет более общий поиск потенциально небезопасных конструкций.

Результаты Semgrep передаются в модуль анализа риска.

### Risk Analyzer

Для каждого Semgrep finding рассчитывается уровень риска на основе доступных характеристик:

* severity;
* impact;
* likelihood;
* confidence.

Результат классифицируется как `LOW`, `MEDIUM`, `HIGH` или `CRITICAL`.

Risk Analyzer используется для приоритизации обнаружений и подготовки данных для AI-анализа.

## 3. Использование LLM

В AI-слое используется выбранная модель семейства Qwen.

LLM не является единственным механизмом определения соответствия требованиям ИБ. Детерминированные проверки ИБ-01 — ИБ-08 выполняются независимо от модели.

AI используется для дополнительной интерпретации результатов статического анализа.

В LLM передаются структурированные данные finding:

* правило;
* файл;
* строка;
* severity;
* impact;
* likelihood;
* confidence;
* описание обнаружения.

AI должен определить:

* является ли finding потенциальным истинным нарушением;
* предполагаемый уровень риска;
* краткое объяснение;
* рекомендацию по исправлению.

Такое разделение уменьшает зависимость критических решений от вероятностного ответа LLM.

## 4. Работа с ограничением контекстного окна

Полный исходный код проекта не передаётся модели одним запросом.

Сначала локальные инструменты выполняют анализ проекта и выделяют потенциально значимые места. Затем в AI передаются только релевантные security findings и необходимые сведения о соответствующем коде.

При большом количестве обнаружений используется обработка порциями.

Общая схема:

```text
Большой проект
      |
      v
Локальный анализ
      |
      v
Выделение findings
      |
      v
Фильтрация релевантных данных
      |
      v
Разбиение на порции
      |
      v
Qwen AI
```

Такой подход позволяет контролировать размер контекста и не связывать его напрямую с общим количеством файлов проекта.

## 5. Формирование отчёта

После завершения анализа Report Generator формирует JSON и Markdown отчёты.

JSON предназначен для автоматической обработки CI/CD.

Markdown предназначен для анализа результатов человеком.

Отчёт содержит:

* идентификатор commit проверяемого проекта;
* время начала и окончания;
* длительность;
* общий результат;
* количество нарушений;
* статус каждого требования;
* конкретные места нарушений;
* результаты дополнительного статического анализа;
* сводку уровней риска.

Commit ID позволяет однозначно связать отчёт с конкретной версией исходного проекта.

## 6. Интеграция с CI/CD

Security Agent запускается отдельным этапом pipeline.

Общий процесс:

```text
Checkout
   ↓
Install dependencies
   ↓
Security Checks
   ↓
Security Agent
   ↓
Security Gate
   ↓
Pipeline result
```

Security Gate использует коды завершения процесса:

* `0` — нарушений требований ИБ не обнаружено;
* `1` — обнаружены нарушения требований ИБ, pipeline блокируется;
* `2` — аварийное состояние, проверка не выполнена корректно.

К аварийному состоянию относятся ошибки разбора проекта, недоступность необходимых компонентов или невозможность получить корректный результат проверки.

## 7. Безопасность самого Agent

Проверяемый проект рассматривается как источник данных только для чтения.

Agent не должен изменять:

* исходный код;
* Git history;
* конфигурационные файлы;
* пользовательские данные проекта.

Отчёты и временные результаты хранятся отдельно от проверяемого проекта.

Секреты и API-ключи не должны попадать в Git или в итоговые отчёты.

## 8. Ограничения прототипа

Решение является прототипом автоматизированного DevSecOps-контроля.

Статический анализ не может гарантировать отсутствие всех возможных уязвимостей, особенно тех, которые зависят от runtime-поведения, инфраструктуры или внешних сервисов.

Semgrep может формировать findings, требующие дополнительной интерпретации.

AI также не заменяет ручную проверку сложных архитектурных решений. Его роль в системе ограничена анализом уже выделенных security findings.

## 9. Итог

Предложенная архитектура объединяет детерминированные проверки требований информационной безопасности, статический анализ и LLM-анализ в единый CI/CD-процесс.

Критические для хакатона требования ИБ проверяются специализированными правилами, а LLM используется как дополнительный аналитический слой.

Результат каждой проверки фиксируется в машиночитаемом отчёте и может использоваться Security Gate для автоматического принятия решения о продолжении или блокировке pipeline.
